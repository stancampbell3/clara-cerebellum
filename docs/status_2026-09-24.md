# Clara stack: development status, 2026-09-24

*A self-contained snapshot for review, written to be ingested into the `assistant.general` knowledge base. Each section stands on its own.
Facts here were checked against the repositories and the running stack on 2026-09-24. Items marked **decision** were made by Stan; items
marked **idea**, **open** or **question** are not decisions. Feedback from Clara on this document is brainstorming input, not a decision.*

## 1. Summary

- **Ritual durability and composition (Approach A) is built.** The eight implementation slices S1 to S8 of the "Ritual properties" spec are
  done, live-verified, committed and pushed. A Ritual can now have a wall-clock deadline, be observed, be cancelled, survive a restart,
  load shared Prolog module fragments, contain child Rituals, and be authored that way in Cobbler. A parent's remaining time budget now
  travels on every Offering to its peers.
- **The Ego (Hermes agent seats behind a gate) runs on pineal, with the gate set to `deny_all`.** A supervised `superego` test showed the gate
  behaves correctly, and also showed that a seat has open internet and LAN access. **Decision:** the gate stays `deny_all` by default until
  seat egress is locked down. Learning and tool governance for Hermes is an open design topic.
- **One operational hazard is known and unresolved at the source:** the shared Prolog library in Dis can be shadowed by a locally defined
  predicate, which silently made the Superego review fail closed. Restarting Dis clears it. Stan expects it to be resolved by locking down
  how Prolog source is loaded.

## 2. Vocabulary (for readers new to this stack)

- **Dis / clara-api**: the Rust service that runs deductions (Prolog + CLIPS), owns Rituals, and persists state in DuckDB.
- **Deduction**: one bounded reasoning run started with `POST /deduce`, driven by the cycle controller.
- **Ritual**: a Kafka topic per Ritual plus a set of participants (evaluators) that exchange typed messages. **Offering** = a request to a
  participant; **Hohi** = success reply; **Tabu** = failure reply. `caws_offer/4`, `caws_await/2` and `caws_consult/4` are the Prolog
  predicates that send an Offering and wait for its correlated reply.
- **FieryPit / lildaemon**: the Python service that hosts evaluators (LLMs, Prolog/CLIPS wrappers, and others) and joins them to Rituals as
  participants. There can be several FieryPits on different hosts.
- **RitualConfig**: a saved, editable definition of a Ritual (a graph of nodes and edges plus settings) that can be activated, run and
  deactivated. Authored in **Cobbler**, the browser editor.
- **Performance**: one run of a Ritual, a goal pursued by a deduction with its participants.
- **Ego / Superego**: the Ego is a Hermes agent seat that acts only through a **gate**; the Superego is the reviewer that approves, denies or
  escalates the actions it requests. **Frontdesk** is the user-facing assistant; the frontdesk-poc analysts are its reasoning rulesets.
- **limbic** is the main host (Dis, main FieryPit, Kafka, Cobbler, Edgequake, GitLab). **pineal** is a second host running an Ego FieryPit.

## 3. Ritual properties: what was built (slices S1 to S8)

The spec is `docs/ritual_properties_spec.md`. The direction, decided by Stan: analysts and other Ritual logic become complete RitualConfigs with
a durable lifecycle, and Rituals compose into Rituals of Rituals.

| Slice | What it gives you | Where |
|---|---|---|
| S1 | A deduction can carry `deadline_ms`; on expiry it ends `expired` with a `reason`. Layered defaults: request, then config, then server ceiling. | Rust (clara-cycle, clara-api) |
| S2 | A Performance is observable: `GET /deduce/{id}` shows its ritual, performance, budget and timestamps. Cancelling sets a flag; expired runs can be resumed. | Rust |
| S3 | Clients cancel a deduction when they stop waiting; a lapsed poll marks pending research failed promptly; RitualConfig has a default deadline. | lildaemon |
| S4 | A RitualConfig can be `persist`. After a lildaemon restart it resumes on the same Dis ritual id, with a `resuming`, `live` or `degraded` runtime state, retry with backoff, and a manual resume endpoint. | lildaemon |
| S5 | Shared Prolog **module fragments** (versioned, hash-locked, checked for collisions with other sources and with the shared library). Also fixed a real bug: resuming a source-id run had loaded no program. | Rust and lildaemon |
| S6 | **Composition data model.** A group node with a `ritualConfigId` is a reference to a child RitualConfig, `owned` (activated and stopped with the parent) or `borrowed` (must already be active). Save-time validation (no cycles, one owner per child, persistence rule), an activation cascade with rollback, and reference guards (409). | lildaemon |
| S7 | **The `ritual` evaluator**: a child Ritual behaves as one participant of its parent, so parent Prolog can `consult` it and the answer returns as Hohi or Tabu. A parent is reported `degraded` while a child is not live, and resume waits for children first. | lildaemon |
| S8 | **Cobbler UI**: Add Child Ritual, ownership, edges to a child, runtime state badge, a persistent checkbox, readable errors. A server guard: a child-reference group cannot also contain nodes. | dagda (Cobbler) and lildaemon |
| Follow-on | **`deadline_ms` on the Offering envelope**: the deduction's remaining budget in milliseconds travels on every Offering; consumers never work past it. | Rust and lildaemon |

**Design decisions recorded along the way (all Stan's):**
- A child Ritual appears to its parent as **one participant**; there is no cross-Ritual addressing.
- Lifecycle is **owned by default, borrowed opt-in**; the reference graph must be a DAG; a child has at most one owner.
- `persist` is per config, default off. `expired` is a distinct, resumable end state.
- The deadline on the wire is a **relative budget**, not an absolute time, so hosts with skewed clocks agree.
- A Ritual's node sources and modules should not be able to override core library predicates (see Section 7).

## 5. The Ego (Hermes) and the gate

- Hermes seats run as containers on their own bridge network and act only through a **gate** (an MCP server in lildaemon) that records every
  decision in an append-only ledger. Gate modes: `deny_all` (default; every requested action is refused) and `superego` (a Prolog policy
  approves an allowlist deterministically and asks a reviewer LLM about free-form or content-flagged actions).
- **Supervised test, 2026-09-24 (pineal, `superego` for one session, then back to `deny_all`):** the allowlisted export was approved and landed in
  the outbox; free-form actions (send email, publish announcement, including one with a self-approving justification) were denied and
  nothing ran; the ledger matched the model's account.
- **Finding, egress:** measured from inside a live seat, the seat can open connections to the **internet**, and to limbic's Dis, Kafka,
  Cobbler and ssh ports. It runs as root inside its container and has `python3` and `curl`. With all toolsets off the model has no tools to
  use them, but that is the wrong thing to rely on for research use. **Decision:** keep `deny_all` as the default until egress is locked
  down. Options are written up in `docs/ego_egress_and_skill_governance.md` (host firewall on the seat bridge, an internal-only network, an
  allowlisting egress proxy, two seat classes, and running code as a gated action in a sandbox rather than in the seat). Recommendation on
  file, not decided: offline seats by default, research seats behind an allowlist proxy, firewall rules as backup, no Python toolset in the seat.
- **Finding, the review path:** the reviewer answered correctly, but the gate denied everything with "the reviewer gave no answer" because
  Dis had a broken shared-library predicate (Section 7). After restarting Dis the real gate **approved the SVG-creation action** as safe and
  **escalated a send-email request** to the user, which is the intended behavior. So the review is sound; a poisoned Dis makes it fail closed.
- **Open, learning governance (raised by Stan):** Hermes learns by default. The goal is to pool what individual instances learn into
  system-wide skills and knowledge, possibly through a genetic-algorithm-like process, so what may be kept, who may promote it and how the
  pool avoids being poisoned all need design. The gate reviews actions but not learning writes. Questions are listed in the egress and
  governance document.

## 6. What is not yet done

- Seat **egress lockdown** (needs host firewall changes that require sudo, which the assistant does not have on pineal).
- **Learning and tool-usage governance** for Hermes, including quarantine, promotion and a fitness signal for pooled skills.
- The parent Performance's deadline is honored by participants and the `ritual` evaluator, but **cancellation is cooperative**: a call blocked
  inside the Prolog runtime (for example `sleep/1`) runs to its end. Time spent in Kafka before a peer receives an Offering is not counted.
- No automated tests exist for the Cobbler frontend; the UI was verified with a headless browser run.
- Not built: remote (other-host) child Rituals; a declarative participant roster; real hash-named Prolog modules (only flat fragments exist);
  a way to reset a terminated config back to draft.
- The **`free_c_string` interface** in the Rust FFI was kept `unsafe` and flagged for a due-diligence pass.

## 7. Known hazards and risks

- **Shared-library shadowing in Dis (unresolved at the source).** A Prolog source that defines a predicate the shared library exports (for example
  `strip_think/2`) shadows the library for every later deduction in that Dis process, until Dis restarts. It happened on 2026-09-24, and the
  source that caused it was not identified. Module fragments are protected against it at activation time; **node sources are not**.
  **Decision (Stan):** source loading will be locked down (users will not edit Prolog directly, and verification happens on save), which should
  resolve it. **Ideas, parked, not to be built now:** reject a config at save time if it overrides core library predicates; a gate self-test
  that reports a poisoned Dis with a specific message instead of "no answer".
- The gate's own tests use a **mocked Dis**, so they did not exercise the live reviewer round trip that the hazard broke.
- Two safety notes from operating: the Dis peer token has appeared once in a session transcript (rotate if it matters), and lildaemon images
  were once built with the local `.env` baked in (now excluded by the Dockerfile ignore file).

## 8. Suggested next steps (candidates, not commitments)

1. Design and implement the **source-loading lockdown** (verify on save), which also settles the shadowing hazard.
2. **Egress lockdown** for seats, then re-run the supervised probe as an acceptance test.
3. A **governance design note** for Hermes learning and tool use: provenance, quarantine, promotion tiers, per-user isolation.
4. Rebuild and re-verify **frontdesk** against the new stack, and exercise the analysts end to end.
5. Optional hardening: the parked gate self-test, and the config-acceptance check.
