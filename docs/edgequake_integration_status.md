1. **`load_rules` fix verified live, and a second, previously-undetected critical bug found and fixed underneath it.**

Root cause: an ABI mismatch that has existed since `clara-evaluate` was first implemented (commit `fe6018c`) — `clara-clips/clips-src/core/userfunctions.c` declares and calls `rust_clara_evaluate(void* env, const char* input)` (two args), but `clara-toolbox/src/ffi.rs` only ever defined `rust_clara_evaluate(input_json: *const c_char)` (one arg). Under the System V x86-64 calling convention, Rust's single parameter reads register `rdi`, which C populates with the CLIPS `Environment*` — the actual JSON string pointer in `rsi` was silently dropped. Every CLIPS-side `clara-evaluate` call has been reading garbage/empty memory as its input for the life of the feature; masked because the only test (`test_clara_evaluate_callback`) asserts `result.is_ok()` but never checks the actual response content.
   - **Fix**: `clara-toolbox/src/ffi.rs` `rust_clara_evaluate` now takes `(_env: *mut libc::c_void, input_json: *const c_char)`, matching the C declaration; the `_env` param is unused (no Rust caller needs it — Prolog's path uses a separate `pl_clara_evaluate` callback, unaffected). Rebuilt `clara-api:latest` and recreated `docker-clara-api-1`.
   - **Verified live end-to-end**: `(ruminate-mode "what is a qubit?" "naive")` from CLIPS now reaches Edgequake and gets back a real structured response (`llm_model: gpt-4.1-mini`, `llm_provider: openai`, timing stats, empty result set since that query isn't in the graph — a data issue, not plumbing). `graph_search_entities` from CLIPS also confirmed working (9,289 total entities). This is the same live round-trip already proven on the Prolog side, now also proven on the CLIPS side.
   - Uncommitted changes so far: `clara-api/src/handlers/session_handler.rs`, `clara-clips/src/backend/ffi/environment.rs` + re-exports (`mod.rs`/`lib.rs`/`backend/mod.rs`), `clara-clips/src/bin/clips-repl.rs` (dedup'd `is_construct`), `clara-toolbox/src/ffi.rs` (this session's ABI fix), `docker/docker-compose.yml` (Edgequake env vars).

## New, smaller findings from this verification pass

- **`the_cow.clp` deffunctions are order-dependent.** Loading the whole file at once fails to build (`CLIPS Build failed (code 3)`) because `ruminate` (defined first) calls `ruminate-mode` (defined third) — CLIPS deffunctions require the callee to already be built, no forward references. Loading `ruminate-mode` alone (or reordering the file bottom-up: `ruminate-mode`, `ruminate-with-context`, `ruminate`) builds fine. Worth fixing the file's definition order, or teaching `load_rules`/callers to build in dependency order.
- **`/sessions/{id}/run` always reports `"rules_fired": 0`, even when a rule genuinely fired.** Confirmed via a rule whose RHS asserted a new fact — the fact appeared, but the API response still said 0. `run_rules` (`clara-api/src/handlers/session_handler.rs`) parses `(run)`'s return value with `result.trim().parse::<u64>().unwrap_or(0)`; likely `env.eval("(run)")` isn't returning the plain fire-count CLIPS returns (e.g. a float string, or captured stdout instead of the return value), silently defaulting to 0 either way. Not investigated further — flagging for a follow-up.

1. **`the_cow.clp` deffunction ordering** — fixed by reordering the file bottom-up (`ruminate-mode`, `ruminate-with-context`, `ruminate`). Verified: loading the whole file in one `POST /sessions/{id}/rules` call now builds successfully (previously `CLIPS Build failed (code 3)`).

2. **`rules_fired` always 0** — root cause was structural, not a parsing slip: CLIPS's `(run)` is registered as a **void-returning** function (`AddUDF(theEnv,"run","v",...)` in `rulecom.c`; `RunCommand` calls `Run(theEnv, runLimit)` and discards the result). `eval("(run)")` can never recover a fire count no matter how its output is parsed. Fixed by binding the underlying `Run(Environment*, long long) -> long long` C API function directly (new `bindings::Run` in `clara-clips/src/backend/ffi/bindings.rs`, new `ClipsEnvironment::run_rules()` in `environment.rs`) and calling that from `run_rules` in `clara-api/src/handlers/session_handler.rs` instead of `eval`. Verified live: a rule with no matching facts reports `rules_fired: 0`; the same rule after asserting a matching fact reports `rules_fired: 1`, matching `(agenda)`'s activation count.

3. **`GET /sessions/{id}/facts` 500s** — root cause: the hardcoded query `(find-all-facts ((?f)) TRUE)` is invalid CLIPS syntax. Per `factqpsr.c`, `find-all-facts`'s fact-variable bindings require `(<var> <template-name>+)` — at least one explicit deftemplate name — and there's no "any template" wildcard, so `((?f))` alone always fails to parse. The endpoint's `pattern` query param was fetched but never actually wired into the query (dead code since it was written). Fixed by switching to `(facts)`, which lists every fact across all deftemplates with no such restriction, and filtering out its trailing "For a total of N facts." summary line from the returned `matches` list. Verified live for both an empty session (`{"matches":[],"count":0}`, previously a 500) and a populated one.

4. **`the_cow.pl`/`the_rabbit.pl` error-detection never fires — confirmed as a real bug, not just "unverified".** Root cause: `atom_json_dict/3` decodes JSON string values as SWI-Prolog **strings** by default, not atoms. Every `get_dict(status, Dict, error) -> fail` check in both files compares against the bare **atom** `error`, which never unifies with a string — so the error branch was dead code. Reproduced in isolation: `atom_json_dict('{"status":"error"}', Dict, []), get_dict(status, Dict, error)` genuinely fails ("Query failed"). Fixed by adding `value_string_as(atom)` to every `atom_json_dict(Raw, Dict, [...])` call that feeds a `get_dict(status, Dict, error)` check: `the_cow.pl`'s `ruminate_with_context/3` and `ruminate_mode/3`, `the_rabbit.pl`'s `classify_text/2` and `classify_text_k/3`. Verified live end-to-end: forcing a real tool error (`{"tool":"classify","arguments":{}}` → `"Tool not found: classify"`) now correctly resolves the `->` branch and reports the error, where before the fix it silently fell through to the success branch.

## Found and fixed (2026-08-11, later same day): `ruminate`/`ruminate_mode` were silently querying unscoped

Stan reported `ruminate_opts/3` (tested via `./target/debug/prolog-repl` + `clara-prolog/examples/ruminate/ruminate.pl`, outside docker) returning a generic "couldn't find any relevant information" for `"what is a clara?"`, while the same question through Edgequake's own GUI gave a real, detailed answer. Traced to a genuine **Edgequake-side bug**, not a clara-cerebellum bug — root-caused by reading Edgequake's own source (checked out locally at `~/moonpool/tools/edgequake`, actual crates under the nested `edgequake/crates/` — the top-level `crates/` dir is a decoy/empty):

- `POST /api/v1/query`'s workspace resolution (`resolve_query_workspace` in `edgequake-api/src/handlers/query/workspace_resolve.rs`) treats a missing `X-Workspace-ID` header as `None` — **fully unscoped**, not "fall back to the Default Workspace." This is inconsistent with graph-read endpoints (`GET /api/v1/graph/entities` etc.), which use `TenantContext::workspace_id_or_default()` and correctly resolve to the Default Workspace UUID when no header is sent. Confirmed via direct `curl` reproduction bypassing all of clara-cerebellum's code: identical empty response with no headers, real detailed answer with the real tenant/workspace UUIDs as headers.
- The `"default"` alias (which some code, `middleware::resolve_workspace_uuid`, explicitly maps to the real Default Workspace UUID) is **not honored on this endpoint** — sending `X-Workspace-ID: default` 400s with `Invalid workspace ID: invalid character: found 'u' at 4`, because a different internal path (`WorkspaceProviderResolver`, per the error shape matching `ProviderResolutionError::InvalidWorkspaceId`) does a raw `Uuid::parse_str` with no alias handling. So the fix requires the **real UUIDs**, not `"default"`.
- This also explains the earlier "Edgequake mislabels which provider served a request" finding from the tenant/workspace plan doc: `stats.llm_provider`/`llm_model` come from a separate `get_workspace_llm_info()` call that *also* falls back to `None` → Edgequake's hardcoded global constants (`DEFAULT_LLM_PROVIDER = "openai"`, `DEFAULT_LLM_MODEL = "gpt-4.1-mini"`, in `edgequake-core/src/types/multitenancy/workspace.rs`) when no workspace resolves — unrelated to the actual per-request `llm_provider`/`llm_model` override, which was working correctly the whole time (confirmed via Edgequake's own resolver logs, `source=Request`). Same root cause, different symptom, not a "mislabeling bug" so much as a second consequence of the same unscoped-fallback design choice.

**Practical impact**: `EDGEQUAKE_DEFAULT_TENANT`/`EDGEQUAKE_DEFAULT_WORKSPACE` (added in the tenant/workspace plan work) were never actually set anywhere, so every plain `ruminate/2`/`ruminate_mode/3` call — not just new `ruminate_opts/3` calls — has been silently querying unscoped since that code shipped. Not a regression from this session's work; a latent bug the new plumbing happened to make fixable.

**Fix applied**: set `EDGEQUAKE_DEFAULT_TENANT=00000000-0000-0000-0000-000000000002` / `EDGEQUAKE_DEFAULT_WORKSPACE=00000000-0000-0000-0000-000000000003` (the real UUIDs, not `"default"`) in `docker/.env` (gitignored, not tracked — set directly, not committed), then recreated `docker-clara-api-1`. Verified live: a plain `use_module(library(the_cow)), the_cow:ruminate_mode("what is a clara?", naive, Result)` — no explicit tenant/workspace args — now returns a real, detailed answer about Clara instead of the generic non-answer.

Worth doing if local (non-docker) `prolog-repl` testing continues to matter, or worth reporting/fixing upstream in Edgequake's own repo (`~/moonpool/tools/edgequake`) since the inconsistent default-resolution and alias-handling behavior between `/api/v1/query` and the graph-read endpoints is a real bug there, independent of anything in clara-cerebellum.
